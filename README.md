# ProNoobs Tournament API

Express and PostgreSQL API for managing Dota 2 tournaments, teams, player identities and MMR, rosters, and registrations. It is designed to be shared by the website and a future Discord bot.

## Requirements and setup

- Node.js 20 or later
- PostgreSQL

From this directory, create the database and apply the schema:

```bash
createdb pronoobs
psql -d pronoobs -f migrations/001_initial_schema.sql
psql -d pronoobs -f migrations/002_team_signup_fields.sql
psql -d pronoobs -f migrations/003_team_logos.sql
pnpm install
```

Copy `.env.example` to `.env`. Set `DATABASE_URL`, create a long random `ADMIN_API_KEY`, and configure `CORS_ORIGINS` with the website's full origin(s), comma-separated. Set `UPLOAD_DIR` to a persistent directory if the deployment filesystem is ephemeral. Start the API with `pnpm dev` for development or `pnpm start` for production. It binds to `127.0.0.1:3000` by default; set `HOST` and `PORT` to override these values.

`GET /health` and `GET /api/health` check the API and database connection.

## Routes

Public read routes:

- `GET /api/tournaments` and `GET /api/tournaments/:id`
- `GET /api/teams` and `GET /api/teams/:id` (include team name, captain's Discord name, agreement acceptance, and five roster members with MMR)
- `GET /api/tournaments/:id/registrations`

All write routes require `X-API-Key: <ADMIN_API_KEY>`:

- `POST /api/tournaments` — create a tournament. Use status `registration_open` to accept entries.
- `PATCH /api/tournaments/:id` — update tournament details, dates, team limit, or status.
- `POST /api/teams` — create a team with `name`, `captainDiscordName`, `captainAgreementAccepted: true`, and exactly five members. Each member needs a `displayName` (the Steam/Dota name) and non-negative integer `mmr`. Optional fields: `discordId`, `steamId`, `position`, and `isCaptain`. The first member is always the captain.
- `PUT /api/teams/:id/logo` — upload one PNG, JPEG, or WebP image as multipart form field `logo` (maximum 5 MB). Returns the team's `logoUrl`; uploading again replaces the previous logo.
- `PATCH /api/players/:id` — update a player's display name, MMR, Discord ID, or Steam ID.
- `POST /api/tournaments/:id/registrations` with `{ "teamId": 1 }` — register an existing team while registration is open and capacity remains.
- `PATCH /api/registrations/:id` with `{ "status": "approved" }` — set registration status to `pending`, `approved`, `rejected`, or `withdrawn`.

Keep the API key on a trusted server or bot. Do not place it in browser code. Direct website writes need user authentication or a server-side form handler first.

## Data model

The first migration creates tournaments, teams, players, team memberships, and tournament registrations. The second adds the captain's Discord name and agreement acceptance timestamp/version. Agreement timestamps are generated by the API and use version `pronoobs-captain-agreement-v1`. The third adds the team's logo storage path. Public team responses return names and MMR but omit player Discord and Steam IDs. Those IDs remain optional and unique in storage. A player can belong to one team roster at a time; each team can have one captain. Registration capacity is checked transactionally.

The captain agreement covers responsibility for the team's participation and organization, best efforts to follow tournament rules including the fair-play MMR cap and a non-toxic environment, and communication with organizers about questions or changes.

## Discord integration architecture

The Discord bot is the always-on process that maintains the Discord Gateway connection and performs role, channel, and message actions. The API stores tournament/team state and serves HTTP requests; it should not hold the bot token or impersonate the Gateway connection. The bot calls the API for reads and writes. When the future website admin panel needs to trigger Discord actions, add a durable job/outbox for the bot to consume, acknowledge, and retry safely. Keep guild IDs, channel IDs, category IDs, and role IDs in bot configuration until the admin panel stores them as editable settings.

Upload a logo with:

```bash
curl -X PUT http://localhost:3000/api/teams/1/logo \
  -H "X-API-Key: your-admin-api-key" \
  -F "logo=@team-logo.png"
```

Team responses include a relative `logoUrl`, such as `/uploads/teams/1/<generated-name>.png`; resolve it against the API origin.

Logo files are stored on disk under `UPLOAD_DIR` (defaults to `backend/uploads`) and served from `/uploads/...`. Keep that directory on persistent storage and include it in deployment backups; the database stores only the file path.

### Same-domain Nginx proxy

For the production URL `https://pronoobs.com/api`, add these locations inside the existing HTTPS `server` block. They send API and uploaded-logo requests to the API on localhost while leaving the static website root in place:

```nginx
location /api/ {
    client_max_body_size 6m;
    proxy_pass http://127.0.0.1:3000;
    include proxy_params;
}

location /uploads/ {
    proxy_pass http://127.0.0.1:3000;
    include proxy_params;
}
```
